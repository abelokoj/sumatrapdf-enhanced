## 2. Proof conventions and change boundaries

**Automated proof** establishes only the exercised geometry, state, bytes, serialization or execution path. For defects, add the smallest relevant regression that fails on the captured pre-change state, then passes on the candidate. Reuse existing Bun/Win32 tests and native C++ assertions. A unit-only test cannot prove user edge dragging, optical alignment or presented frame cadence.

**Visual inspection** uses actual native captures, approved original references, recorded DPI/font/theme and actual saved document rendering. **Real-device testing** covers physical pointer drag, mixed-monitor DPI, touchpad/pen and assistive technology where applicable. **Maintainer acceptance** decides visual fitness, reference matching and any explicitly unresolved product choice. Each acceptance record must say which of these tiers passed, failed or was not exercised. Compilation and unrelated assertion totals close none of the behavioral criteria.

Use private profiles and disposable copies for write tests. For document changes, reopen saved bytes in Sumatra and an independent compatible reader/validator; identify reader/version. Inspect format structures where visual reopening alone can conceal loss. Preserve sources on cancellation/failure. Do not edit vendored code without its required `ext/patches` record. Command/settings generators are authoritative; coordinate generated output rather than hand-editing it independently.

Future dependency or engine changes must follow the repository/skill rules after a concrete option is available. Ordinary metric repairs do not need a new design exploration. No parallel workers may write the same shared file. GUI probes and performance measurements run serially.
